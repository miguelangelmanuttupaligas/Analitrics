PRUEBA 1 - VALIDACION DE CARGA DE ARCHIVOS HASTA DUCKDB
Fecha: 2026-08-21
Ambiente: local docker compose Analitrics
Objetivo: validar el flujo LibreChat/RustFS/Mongo -> agente -> DuckDB -> catalogo Postgres sin llegar al LLM.

Resumen ejecutivo
=================
Resultado final: 11 casos pasaron, 1 caso fallo.

El flujo principal funciona para:
- XLSX real de una hoja.
- XLSX real de varias hojas.
- Varios XLSX en el mismo contexto DuckDB.
- CSV con coma.
- CSV con punto y coma via DuckDB read_csv_auto.
- Pregunta posterior sin re-adjuntar archivo, resolviendo contexto previo de la conversacion.
- Conversacion sin archivo con error controlado.
- Aislamiento por tenantId.
- Cache DuckDB por sesion.
- Archivo XLSX corrupto con error especifico de etapa.
- Persistencia de catalogo/perfil en Postgres.

El fallo real encontrado:
- Aislamiento por userId: otro userId dentro del mismo tenant pudo resolver un file_id ajeno.

Alcance de la prueba
====================
No se probo el punto de borrado/invalidation de archivos porque fue excluido explicitamente.

La prueba se ejecuto contra el servicio de ingesta/validacion del agente, sin LLM:
- llmUsed=false en todos los casos.
- Se valido que los archivos terminen en DuckDB.
- Se valido que el catalogo/perfil se persista en Postgres.
- Se valido que la metadata base venga desde Mongo.
- Se valido que los objetos originales existan en RustFS/S3 compatible.

08_isolation_other_user - FALLO
Descripcion: otro userId no deberia poder resolver file_id ajeno.
Esperado:
- Error No S3 file metadata.

Resultado real:
- El otro userId resolvio el archivo d98d15ef-ea3a-4eca-8d55-42518f86d1a1.
- Se creo DuckDB en:
  /var/analitrics/analytics/cache/analitrics/_6a8097c5324af6e6b24859eb_other/analitrics_prueba1_carga_other_user.duckdb
- cacheHits=1
- Catalogo Postgres persistido bajo ese otro userId.

Motivo probable:
El resolver de metadata consulta Mongo por tenantId + source + file_id, pero no filtra por user/owner. Como el file_id es suficiente dentro del mismo tenant, cualquier userId que conozca un file_id puede resolverlo.

Riesgo:
Alto para aislamiento entre usuarios del mismo tenant. Aunque hoy el producto agrupe usuarios en tenant analitrics, un usuario no deberia poder leer archivos privados de otro usuario solo por conocer file_id.

Propuesta de mejora:
- Endurecer resolve_file para exigir owner cuando no exista un modelo explicito de archivos compartidos.
- Query minima esperada en Mongo:
  tenantId + source=s3 + file_id + user=req.user.id
- Si a futuro hay archivos compartidos, introducir permisos explicitos:
  ownerUserId, sharedWithUsers, sharedWithGroups, tenantWide=false/true.
- La cache DuckDB ya queda aislada por userId en ruta, pero eso no basta si antes se permite resolver metadata ajena.

Catalogo en Postgres
====================
Se encontraron perfiles persistidos en:
- analysis_catalog_sessions
- analysis_catalog_profiles

Sesiones detectadas para esta prueba:
- analitrics-prueba1-carga-cache-session: 2 perfiles activos
- analitrics-prueba1-carga-csv-comma: 4 perfiles activos
- analitrics-prueba1-carga-csv-semicolon: 4 perfiles activos
- analitrics-prueba1-carga-debug: 2 perfiles activos
- analitrics-prueba1-carga-followup: 2 perfiles activos
- analitrics-prueba1-carga-two-xlsx: 5 perfiles activos
- analitrics-prueba1-carga-xlsx-multi: 4 perfiles activos
- analitrics-prueba1-carga-xlsx-simple: 2 perfiles activos

Descubrimiento:
Los perfiles de csv-comma/csv-semicolon aparecen con 4 perfiles activos porque hubo una corrida previa con otros file_id fixture bajo el mismo session_id de prueba. Como no se ejecuto invalidacion de archivo ni limpieza de Postgres para esta prueba, los perfiles previos quedaron activos.

Lectura:
Esto no invalida el flujo principal, pero muestra que las pruebas repetidas con la misma session_id y nuevos file_id pueden acumular catalogo en Postgres si se siembran fixtures manualmente.

Propuesta:
- Para test suites, limpiar catalogo por prefijo/session_id antes de correr.
- Para producto real, mantener la invalidacion por borrado/logical delete cuando se borren archivos.
- Para reingestas, definir una politica clara: misma session + nuevo file_id suma contexto; archivo borrado/despublicado se marca inactive; TTL limpia DuckDB fisico.

Conclusiones
============
1. El flujo de carga/ingesta hasta DuckDB funciona para XLSX y CSV.
2. El XLSX multi-hoja funciona creando una tabla por hoja.
3. El catalogo tecnico se persiste en Postgres con claves tenant_id, user_id, session_id.
4. El hash real del contenido se esta calculando y exponiendo como contentHash.
5. La cache DuckDB por sesion funciona.
6. La recuperacion de archivos desde mensajes anteriores de la conversacion funciona.
7. Los errores de archivo corrupto son especificos y accionables.
8. El aislamiento por tenantId funciona.
9. El aislamiento por userId no funciona y debe endurecerse antes de considerar el flujo robusto.

Addendum de correccion - 2026-08-21

Se corrigio el hallazgo P0.

Cambio aplicado:
- resolve_file ahora incorpora owner en el query de mongodb.files cuando el request trae user_id.
- Como LibreChat guarda files.user como ObjectId, el filtro soporta ambos formatos:
  user string y ObjectId(user_id).
- El filtro efectivo queda conceptualmente:
  tenantId + source=s3 + file_id/filename + user in [user_id, ObjectId(user_id)]

Validacion posterior:
- Usuario owner:
  userId=6a8097c5324af6e6b24859eb
  file_id=d98d15ef-ea3a-4eca-8d55-42518f86d1a1

  userId=6a8097c5324af6e6b24859eb-other
  file_id=d98d15ef-ea3a-4eca-8d55-42518f86d1a1
  Resultado: BLOQUEADO con:
  No S3 file metadata found for query: {'tenantId': 'analitrics', 'source': 's3', 'user': {'$in': ['6a8097c5324af6e6b24859eb-other']}, 'file_id': 'd98d15ef-ea3a-4eca-8d55-42518f86d1a1'}

Lectura:
El path de RustFS ya incluye el id del usuario propietario:
t/analitrics/uploads/<ownerUserId>/<file_id>__<filename>
pero la proteccion no debe depender solo del path. El bloqueo correcto ahora ocurre antes, al resolver metadata en Mongo por owner.

Addendum de prueba semantica multiarchivo - 2026-08-21
======================================================
Se ejecuto la prueba pendiente con el agente completo, incluyendo LLM, generacion SQL, ejecucion DuckDB, critica y chart_spec.

Pregunta:
Compara los ingresos totales por producto entre data_2023.xlsx y data_2024_2026.xlsx. Devuelve los 10 productos con mayor diferencia absoluta e indica en que archivo son mayores los ingresos.

Archivos usados:
- data_2023.xlsx
  file_id=47d28c52-5ebd-47f4-b72c-bcb1a0b0901c
- data_2024_2026.xlsx
  file_id=d98d15ef-ea3a-4eca-8d55-42518f86d1a1

Resultado tecnico:
- in_scope=true
- files resueltos=2
- tablas disponibles=5
- DuckDB cache:
  /var/analitrics/analytics/cache/analitrics/_6a8097c5324af6e6b24859eb/prueba1_semantic_multiarchivo.duckdb
- SQL generado y ejecutado correctamente.
- row_count=10
- critic.approved=true
- chart_spec.chart_required=true

SQL ejecutado:
SELECT
  COALESCE(i23.producto, i2426.producto) AS producto,
  COALESCE(i23.ingresos_data_2023, 0) AS ingresos_data_2023_xlsx,
  COALESCE(i2426.ingresos_data_2024_2026, 0) AS ingresos_data_2024_2026_xlsx,
  COALESCE(i2426.ingresos_data_2024_2026, 0) - COALESCE(i23.ingresos_data_2023, 0) AS diferencia_data_2024_2026_menos_data_2023,
  ABS(COALESCE(i2426.ingresos_data_2024_2026, 0) - COALESCE(i23.ingresos_data_2023, 0)) AS diferencia_absoluta,
  CASE
    WHEN COALESCE(i23.ingresos_data_2023, 0) > COALESCE(i2426.ingresos_data_2024_2026, 0) THEN 'data_2023.xlsx'
    WHEN COALESCE(i2426.ingresos_data_2024_2026, 0) > COALESCE(i23.ingresos_data_2023, 0) THEN 'data_2024_2026.xlsx'
    ELSE 'Iguales'
  END AS archivo_con_mayores_ingresos
FROM (
  SELECT
    producto,
    SUM(COALESCE(monto, 0)) AS ingresos_data_2023
  FROM "data_2023__47d28c52_data_2023_data_2023"
  GROUP BY producto
) AS i23
FULL OUTER JOIN (
  SELECT
    producto,
    SUM(COALESCE(monto, 0)) AS ingresos_data_2024_2026
  FROM "data_2024_2026_d98d15ef_data_2024_2026_hoja1"
  GROUP BY producto
) AS i2426
  ON i23.producto = i2426.producto
ORDER BY diferencia_absoluta DESC, producto
LIMIT 10;

Respuesta obtenida:
Los 10 productos con mayor diferencia absoluta fueron todos mayores en data_2024_2026.xlsx. El top incluyo:
1. Especializacion Power Apps y Power Automate: 469,320
2. Analitica de Datos de Recursos Humanos - MEF: 450,000
3. Data Storytelling - Pacifico Salud: 447,300
4. Data Practitioner - LAP: 416,000
5. Especializacion en Power BI: 357,692

Lectura de calidad:
El flujo resolvio correctamente archivos, tablas, SQL y ejecucion. Para una pregunta multiarchivo, el SQL es razonable: agrega por producto, compara ambos archivos con FULL OUTER JOIN, calcula diferencia absoluta y ordena.

Limite detectado:
data_2023.xlsx contiene varias hojas con columnas similares. El agente eligio la tabla:
data_2023__47d28c52_data_2023_data_2023
No tenemos aun un catalogo certificado ni feedback de usuario que indique que esa hoja es la fuente oficial para comparar 2023. Por eso, aunque el SQL sea tecnicamente correcto, no se puede certificar semanticamente que la hoja escogida sea siempre la correcta.

Conclusion:
El flujo de resolver archivos ya esta en muy buen estado para MVP: metadata, owner, RustFS, DuckDB, cache, profiling y Postgres funcionan. La calidad del SQL esta en el techo razonable del estado actual. Para mejorar mas se necesita incorporar feedback de usuario, catalogo/diccionario certificado, reglas de hoja oficial y conceptos de negocio validados.
